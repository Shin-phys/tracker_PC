# MotionTrace Pro Ver.2（PC 版）

動画内の最大 5 個の物体を自動追跡し、位置・速度・相対距離を取り出す Web アプリです。
物理実験のマーカー追跡を想定しています。ブラウザだけで動き、動画はサーバへ送られません。

スマートフォン専用版は [tracker_mobile](https://github.com/Shin-phys/tracker_mobile) にあります。
追跡・校正・平滑化のアルゴリズム（`src/utils/`）は両者で同一なので、同じ動画からは同じ数値が出ます。

## 起動

```bash
npm install
npm run dev
```

ビルドは `npm run build`（`tsc` の型チェック → `vite build`、出力は `dist/`）。

## 追跡（自動）

1. 動画を読み込む
2. 追跡したいマーカーを囲む（**20px 以上**、できれば 30px 前後）
   - **ドラッグ** — 対角にドラッグして一気に引く
   - **クリック** — 中心だけ先に決め、スライダーで大きさを合わせて「決定」
3. 再生する

### 虫めがね

点を置くあいだ、カーソルの周りを **3 倍に拡大**した窓が映像の隅に出ます。
画素の境目が見えるように補間を切ってあります。どの画素を指しているかが
分からないと、1px の精度では置けません。

2 点間校正でとくに効きます。基準が 33px しかない画では **1px が 3%** に
なります。目分量のドラッグでは端が決まらないので、中心や端点を先に決めて、
拡大しながら合わせてください（矢印キーで 1px、Shift + 矢印キーで 10px 動かせます）。

小さすぎる枠は画面上のどこにでも一致してしまい、軌跡が暴走します。囲めない大きさのときは、
先に拡大してから囲んでください。

**枠の中は、マーカーと一緒に動くものだけで埋めてください。** カメラが固定で物体が動く以上、
枠に写り込んだ背景は次のコマでは必ずずれていて、照合を前のコマの位置へ引き戻します。
合成データでの実測では、同じ枠の大きさでも、枠が物体の面で埋まっていれば誤差 0.011px、
動かない背景が入ると 0.139px でした（13 倍）。枠を広げるとこの差は 34 倍まで開きます。

台車のようにマーカーを貼る面が広い対象なら、枠を大きく取って構いません
（他の場所と紛れにくくなるぶん有利です）。小球や細い棒のように、枠がどうしても背景を
含んでしまう対象では、**枠をマーカーぎりぎりまで詰める**のが正解です。

取り直したいときは **「やり直し」**（軌跡を消し、枠を戻る先のコマの位置へ戻して始点へ送ります）。
軌跡を消さずに戻るだけなら **「始点へ」**。どちらもボタンに行き先の時刻が出ます。

### 速い対象: 初速を教える

トラッカーは**等速度予測**を持っていますが、最初の 1 コマだけは速度がまだ無く、
予測なしで「前のコマと同じ場所」を中心に探します。1 コマの移動量が探索窓
（枠の大きさ × 探索範囲）を超える対象は、**ここで必ず破綻します**。
投げた直後の球、衝突直後の台車などがこれに当たります。

映像下の **「2点目を指す」** を押すと、枠を置いたコマから数コマ送った状態になります。
そこで**枠から、対象が移動した先までドラッグ**すると矢印が引かれます。
この矢印が「数コマでどれだけ動いたか」で、ここから 1 コマあたりの移動量が決まり、
追跡の最初のコマから予測が効くようになります。
離すと、記録が始まるコマへ自動で戻ります。

効き目はもう一つあります。予測が当たっている限り、探索窓が吸収すべきなのは
「移動量」ではなく**「移動量の変化」**だけで済みます。実測した自由落下では
44px/コマ に対して 1.1px/コマ、40 倍の差でした。探索窓を小さく保てるぶん、
背景の似た模様に吸われる確率が下がります。

静止から始まる運動（自由落下など）では要りません。1 コマの移動量が対象より
大きいときだけ、「このままでは追えません」と出ます。それ以外は黙ります。

**指した点は検算にも使われます。** 再生してその時刻に来たとき、追跡位置が
指した位置から離れていたら「別のものを掴んでいます」と警告します。
マッチングスコアは高いまま別の物を追えてしまうので、**走らせた直後に
間違いへ気づける手がかりはこれだけ**です。

やり直しをすると、戻る先のコマでの速度が軌跡から拾い直されます。

### 取りこぼしをゼロにする — 「全コマ処理」

再生しながらの処理は `requestVideoFrameCallback` に乗っているので、1 フレーム分の処理が
実時間のフレーム間隔に間に合わないと、その間に提示されたコマは**呼ばれないまま通り過ぎます**。
「再生速度を落とすとうまく追える」のはこれが理由で、遅くするのは取りこぼす確率を
下げているだけで、ゼロにはなりません。

**「全コマ処理」** は再生せずに「次のコマへシーク → 処理」を繰り返すので、
端末の速さに関係なく取りこぼしが原理的に起きません。そのぶん実時間はかかります
（1 コマあたり数十 ms のシーク待ち）。解析区間を指定していればその範囲だけを処理し、
途中で「中止」できます。

合成動画（480×320・30fps・3 秒 = 90 コマ）を実際に処理させた実測です。

| やり方 | 記録できたコマ |
|---|---|
| 再生 1× | 41 / 90（46%） |
| 再生 1/4× | 88 / 90（98%） |
| **全コマ処理** | **90 / 90（100%）** |

再生速度は 1/16 まで選べます（1/16 は Chrome が受け付ける下限で、それより遅い値は
例外になります）。それでも足りないときは速度ではなく「全コマ処理」を使ってください。

画面上の追跡点・手動記録の点・修正の点は、**中心に隙間のある十字**で描いています。
塗りつぶした丸だと、狙っている画素そのものが自分の描画で隠れてしまうためです
（測量のレチクルや画像編集ソフトの精密カーソルが例外なくこの形なのと同じ理由）。
自動追跡の精度には影響しませんが、手で打つ・直すときの精度は変わります。
手動記録の誤差は 1/Δt² で速度・加速度へ拡大するので、クリックのばらつきが半分になれば
同じコマ送り幅で速度の誤差もそのまま半分になります。

追跡が外れたら、一時停止して「修正」ツールで点を正しい位置へドラッグします。
その位置でトラッカーを作り直すので、そこから追跡を続けられます。記録済みデータも書き換わります。
修正できたかどうかは画面上部の帯に出ます。

画面外に出た物体は `exited` として追尾を打ち切り、軌跡もそこで終端します。

## 追跡（手動記録）

自動追跡が使えない対象（変形する物体、低コントラスト、遮蔽が多い）はコマごとに手で指します。
映像下の **「手動記録」** から入ります。

1. コマごとに対象をクリックする
2. その コマの全対象を打つと、自動で設定コマ数だけ進む
3. 動画を 1 周すれば終わり

- 打つ順番は `Obj1 → Obj2 → …` と案内されます。**物体チップを押せば順番を飛ばして指名**できます
  （1 回限り。打つと自動の順番へ戻ります）
- **取り消し**で 1 点ずつ遡れます
- 記録は自動追跡と同じデータに入り、CSV の `Manual` 列で区別できます。
  **自動で 7 割追って、追えない区間だけ手動で埋める**という使い方ができます

### コマ送り幅が精度を決めます

加速度は位置を 2 回微分して出すので、クリックのぶれが 1/Δt² で拡大されます。
**細かく打つほど良い、ではありません。** 合成データ（自由落下・240fps 撮影・クリック精度 ±0.6px・40 点）
で重力加速度を推定したときのばらつきです。

| 何コマおき | 実時間の間隔 | ばらつき |
|---|---|---|
| 1 コマ | 4.2 ms | 40.7 % |
| 2 コマ | 8.3 ms | 11.4 % |
| 4 コマ | 16.7 ms | 2.7 % |
| **8 コマ** | **33.3 ms** | **0.7 %** |
| 16 コマ | 66.7 ms | 0.2 % |

偏りは出ない（平均は常に真値）ので、問題はばらつきだけです。目安として **実時間で 30〜50ms** 空けます。
スライダーには実時間の間隔が併記され、短すぎる設定は警告色になります。
撮影 fps から推奨値が自動で入ります（通常 30fps なら 1 コマ、240fps スローなら 10 コマ）。

## マーカーの選び方

7 種類の形状を、このアプリの照合アルゴリズムそのもので 12,400 回試行して比べました
（`scripts/marker-benchmark/`）。

| 状況 | 推奨 | 位置誤差 |
|---|---|---|
| 回転しない対象（台車・落とす箱） | **太い十字**（腕幅 = 径の 1/4） | 0.069 px |
| 回転する対象（球・輪・振り子のおもり） | **同心円**（白 D / 黒 0.62D / 白 0.31D） | 0.078 px |
| 迷ったとき | **白地に黒丸**（黒の径 = 0.6D） | 0.116 px |
| （現行）白い丸シール | 非推奨 | 0.251 px |

大きさは画面上で **20〜30px** になるように作ります。
実寸 = 視野の横幅 [mm] ÷ 横の画素数 [px] × 25。線幅は画面上で 3px を切らないこと。
`scripts/marker-benchmark/marker_sheet.pdf` を実寸（100%）で印刷すれば、
10〜32mm の 6 サイズが切り取り線付きで出ます。

### 注意すべき 2 点

- **回転する対象に十字・市松・4分割を使わないでください。** いまのトラッカーは回転不変ではないので、
  15° 回っただけで一致度が 0.98 → 0.51 まで落ちます（LOST 判定は 0.45）。
  同心円と丸は 0.97 以上を保ちます。
- **方眼紙や目盛りのある背景では、白い丸シールが破綻します。** 実測で 150 回中 100 回、
  1px 以上外しました。相関のピークが格子の交点に引っ張られるためです。印刷したマーカーは
  7 種すべて破綻ゼロでした。

なお、形状の差（最大 4 倍）よりも**枠の中身**（13〜34 倍）のほうが一桁効きます。
まず枠の取り方を直してから、形状を検討してください。

## スケール校正

3 モードあります。

- **平面（四隅）** — 基準の四角形の四隅を 左上 → 右上 → 右下 → 左下 の順にクリック。
  射影変換で遠近を補正するので、**斜めから撮った映像でも正しい実寸**が出ます。
- **2点間** — 既知の長さを 2 点で指定。光軸が運動面に垂直なときだけ正しい値になります。
- **追跡枠の幅** — 枠の幅を基準にする簡易モード。

置いた点は掴んでドラッグできます。クリックして選ぶと、**矢印キーで 1px**、
**Shift+矢印で 10px** 動きます（Tab で次の点、Esc で選択解除）。
選んでいる点は映像上で太く描かれるので、どちらを動かしているか取り違えません。
斜めから撮った映像では必ず平面校正を使ってください。2点間校正では遠近の分がそのまま誤差になります。


### 基準は長く取ってください

縮尺は「実寸 ÷ 基準のピクセル長」なので、**校正の誤差は基準の長さに反比例します。**

| 基準の長さ | 端を 1px ずらしたときの誤差 |
|---|---|
| 33 px（2cm の球） | 3.0 % |
| 100 px | 1.0 % |
| 500 px（30cm の物差し） | 0.2 % |

この誤差は長さだけでなく、**速度にも加速度にもそのままの倍率で乗ります**。
直径 2cm の球を基準にして両端を 4px ずつ外に取ると 24% ずれ、重力加速度が
9.8 ではなく 7.9 になります。実際に起きた話です。

基準が 150px を切ると警告を出します。定規や、両端に十字を印刷したスケールバーなど、
**長くて端が一意に決まるもの**を基準にしてください。

校正点は**中を塗らない十字**で描いています。塗りつぶした丸だと、狙っている目盛りが
自分の描画で隠れ、終点が目分量になります。それがそのまま上の誤差になります。

### 原点

映像下の **「原点」** で、座標の原点にしたい位置をクリックできます（斜面の始点、レールの目盛り 0 など）。
CSV の `X, Y` がその点からの値になるので、表計算側でオフセットを引く手間がなくなります。

未指定なら従来どおり画像の左下（`Y軸を上向き` が OFF なら左上）が原点です。
平面校正では射影変換したあとに平行移動するので、遠近がかかっていても正しく効きます。
動画を読み込み直すと解除されます（画像座標なので別の動画では意味を持たないため）。

## 解析区間（時間範囲）

任意です。指定しなければ従来どおり動画全体を使います。

実験動画の頭と尻には、必ず使えない時間が入ります。装置の準備、手がフレームに入っている区間、
着地後の跳ね返り、転がって止まるまで。これを含んだまま解析すると 2 つが壊れます。

- **Butterworth の自動遮断周波数** — 残差の Durbin-Watson を最小化する方式は、記録全体に対して
  遮断周波数を 1 つ選びます。静止区間や衝突の不連続が混ざると、そちらに引きずられて
  肝心の運動区間に対して不適切な値が選ばれます。
- **中心差分** — 衝突の瞬間をまたいだ 1 点だけ、物理的に意味のない速度が出ます。

区間を切るのは見た目を整えるためではなく、この 2 つを避けるためです。

### 使い方

映像下の再生バーの下にある **「解析区間」** から指定します。

1. 運動が始まるコマまでコマ送りし、**「始点にする」**
2. 運動が終わるコマまで進めて、**「終点にする」**

指定した秒数のボタンを押すとその位置へ飛ぶので、目で確かめられます。**「解除」** で動画全体に戻ります。
片側だけの指定（始点だけ／終点だけ）もできます。シークバーには区間が帯で表示されます。

記録するのは「いま画面に出ているフレームの時刻（mediaTime）」なので、
要求した時刻ではなく実際に表示されたコマが境界になります。

### 何に効くか

区間は **記録と解析の両方**に効きます。

| | 動き |
|---|---|
| 記録 | 区間外は追跡も記録もしない。**終点で自動停止**する |
| 再生 | 区間の外から再生を始めると、まず始点へ送ってから再生する |
| やり直し | 動画の先頭ではなく**区間の始点**へ戻る（軌跡は消え、枠はそのコマで物体がいた位置へ戻る） |
| 解析 | グラフ・フィルタ・CSV が区間内のデータだけを使う |

終点の自動停止があるので、「終わりを目で見張って一時停止を押す」操作が要りません。
押し遅れて余分なフレームが混ざる事故もこれで消えます。

**あとから狭めるのは非破壊です。** 記録済みのデータは残っているので、区間を狭めれば
グラフ・フィルタ・CSV がその区間だけを使うようになり、広げれば元に戻ります。取り直しは不要です。
区間が効いているときは、データパネルの先頭と CSV の説明にその旨が出ます。

### 短くしすぎない

区間内が **20 点を切ると警告**が出ます。Butterworth はデータから遮断周波数を決めるので、
点数が減ると選択そのものが不安定になります。区間を広げるか、コマ送り幅を細かくしてください。

区間は画像ではなく「この動画の何秒から何秒まで」なので、動画を読み込み直すと解除されます。

## やり直し（取り直し）

映像下の **「やり直し」** は 3 つを同時に行います。

1. 記録した軌跡を消す
2. **追跡枠を、戻る先のコマで物体がいた位置へ戻す**
3. 記録が始まる時刻へ送る（区間の始点 → 無ければ枠を引いたコマ → 無ければ先頭）

2 が要る理由は、`roi` が追跡中に毎フレーム上書きされるからです。追跡が終わった時点で
枠に入っているのは「物体が最後に到達した位置」なので、それを残したまま巻き戻すと、
物体のいない場所でテンプレートが作り直され、その場で破綻します。

**戻す先は 2 段階です。**

- 直前の走行の軌跡が残っていれば、**戻る先のコマ（＝ 3 の時刻）でその物体がいた位置**へ
  枠を移します（大きさは変えません）。
- 軌跡がまだ無ければ、枠を引いた瞬間の矩形 `initialRoi` へ戻します。

`initialRoi` へ戻すだけだと、区間の始点をあとから動かした場合や、物体ごとに別のコマで
枠を引いた場合に、**枠と映像が別のコマを指したまま**になります。これが
「やり直すたびに枠を置き直す」原因でした。

結果として **同じ区間・同じ初期枠なら、何度取り直しても同じ数値が出ます。**
フィルタの設定や再生速度を変えて比べるときは、この再現性が前提になります。

手動で打った点があるときは、消える点数を示して確認します（手動記録は取り消しが高くつくため）。

### 枠を引いたコマと区間の始点

テンプレートは **枠を引いた瞬間のコマの画**から作られます。区間の始点がそのコマとずれていると、
始点のコマに物体がいない＝追跡が始まらない、ということが起きます。
ずれているときは警告と **「枠のコマを始点にする」** ボタンが出ます。

複数の物体の枠を別々のコマで引いた場合も警告します。戻れるコマは 1 つしかないので、
どちらかは必ず外れます。同じコマまで戻して引き直してください。


## コマの点検

記録が終わると、**位置の 2 階差分**が一定かどうかを自動で調べます。等加速度なら
これは一定になるはずなので、飛んでいるコマは次のどちらかです。

1. **動画側のコマの時刻ずれ** — スロー撮影を焼き直した動画には、ときどき半コマ分
   ずれた絵が混ざります。実測した例では、240fps 刻みの素材を実効 120fps へ間引く
   過程で、素材のコマが欠けている場所だけ隣の絵が使われていました。
   **追跡がどれだけ正確でも、これは動画に焼き込まれているので消せません。**
2. **追跡の失敗** — ブレて別のものに一致した、画面端で止まった、など。

該当するコマは映像上で**橙の破線**で囲みます。点は消しません。消すと「無かったこと」に
なり、なぜ速度が暴れているのか説明できなくなるからです。

速度に直してから探さないのは、微分がノイズを増幅するうえ、中心差分のせいで
1 コマの異常が前後 2 点へ逆向きに散り、原因のコマが特定できなくなるためです。

### ブレの限界

**1 コマの移動量が枠の 0.7 倍を超えた時刻**も併せて出し、区間の終点として提案します。
対象が自分の大きさ以上に流れて写ると、テンプレート照合の中心はもう対象の中心では
ありません。ここから先のデータは、追跡できているように見えても使えません。

対策は「明るくする」「撮影 fps を上げる」「対象を大きく写す」のどれかです。

## 追跡が暴れたら止まります
追跡が飛んだコマを見つけたら、**その場で再生を止めます**。

判断に使っているのは 2 つです。

- **相関のピークが探索窓の縁に出た** — 本当の最適解が窓の外にあるかもしれない、
  つまり追い切れていない状態。サブピクセル補間も効かないので、座標が整数に
  なって現れます。実際の衝突動画では、暴れたコマの多くがこれでした
- **1 コマの移動量が、直前までの中央値から大きく外れた**（3 倍以上）

マッチングのスコアは高いまま壊れるので、ロスト判定では拾えません。

### 衝突と見分ける

**飛んだのが 1 つだけなら追跡の失敗、2 つ以上が同じコマで飛んだら衝突**として
扱い、止めません。運動量のやりとりは同時に起きるので、本物の衝突では
両方の速度が同じコマで変わります。片方だけが飛ぶのは物理的に起こりません。

実際の衝突動画（2 物体）で確かめたところ、暴れた 4 コマをすべて拾い、
衝突そのものは 1 件も誤検出しませんでした。

### 止まったあと — 直すのではなく捨てる

飛んだコマには **✕** を付け、**軌跡の線をそこで切ります**。点そのものは消しません。
消すと「無かったこと」になり、誤検出だったときに戻せません。

そのうえで案内に 3 つ出ます。

- **ここから取り直す** — 戻す位置を選ぶ画面に入ります（下記）
- **この点を手で直す** — そのコマへ送って修正モードに入ります
- **誤検出・続ける** — ✕ を外し、同じあたりでは当分検出を見送ります
  （見送らないと、再開した次のコマで同じ理由でまた止まります）

### 戻す位置の選び方

直前の記録点が候補として映像の上に並びます。**判断の基準はひとつだけです。**

> **点がマーカーに乗っている最後のコマ**

1. **アプリが答えを置いています** — 移動量が普段から外れ始めた 1 つ手前が
   最初から選ばれています（白い二重の輪）。そのままで良ければ 3 へ
2. 違うと思ったら **← →**（または点をクリック）で動かします。
   選択を動かすと**そのコマへ動画が送られ**、虫めがねが選択中の点を
   拡大するので、点がマーカーの上に乗っているかを見て決められます。
   赤い点は移動量が普段から外れたコマです
3. **「ここで切る」**（または Enter）。それより後の記録を捨て、
   枠をその位置へ戻します
4. 枠を置き直して再生を続けます

候補を選ぶとそのコマへ送るのは、**この判断が映像を見ないと決められない**
からです。止まったコマのまま点だけを並べても、どれが正解なのかは分かりません。

### 捨てたコマを手で埋める（橋渡し）

切ったあと、**同じコマをもう一度自動で追わせても同じ結果になります**。
壊れた理由は「そのコマの画と、そのコマの動きの大きさ」で決まっていて、
枠を引き直してもどちらも変わらないからです。枠の位置そのものは記録から
分かっているので、置き直しても新しい情報はありません。

**本当に足りないのは「跳ねたコマで対象はどこに居たのか」です。**

そこで切ったあとは、**捨てたコマを人が指して埋めます**。捨てた最初のコマが
出るので、対象の中心をクリックしてください。そのコマの対象が揃うと
1 コマ進みます。2〜3 コマ指したら **「自動に戻す」**。

難しいコマを自動に任せないことで、3 つが同時に片付きます。

1. **捨てたコマが本来の位置で埋まる** — データに穴が開きません。
   2 階差分も当てはめも、穴があると前後 2 点に影響が散ります
2. **最後の 2 点から 1 コマあたりの移動量が出る** — 再開の初速になります。
   トラッカーは直前のコマからの変位を予測に使うので、作り直した直後の
   1 コマだけは予測がありません。止まった場所はまさに予測が外れた場所です
3. **テンプレートを「難しい場面の先」で作り直せる** — 衝突やブレの瞬間を
   自動で越えさせる必要がなくなります。ここが一番効きます

複数の対象があるときは、各コマで全部を指してもらいます。1 つだけ埋めて
コマを進めると、もう一方にだけ穴が開いた記録になり、2 物体間の距離も
「同じコマの組」も崩れるからです。

そして自動に戻す瞬間に、**その枠が本当にその対象を見つけられるかを実測します**。
最初に指したコマのテンプレートを、最後に指した位置で探してみます
（どちらの位置も人が教えてくれているので測れます）。

測り方は、ピークの**鋭さ**です。

```
鋭さ ＝ (指した位置の相関) − (テンプレートの 35% だけずらした 8 方向の平均)
```

枠の中に「コマが変わっても形の変わらないもの」が入っていなければ、ずらしても
相関が落ちません。**どこへずれても同じくらい一致する**ので、スコアは高いまま
位置だけが流れます。ロスト判定には引っかかりません。

合成データでの実測（別ノイズを乗せた 2 コマ間で測定）

| 枠の置き方 | 鋭さ |
|---|---|
| 一様な物体の内側だけを枠 50 で囲む | **−0.03** |
| 同じ物体を輪郭まで含めて枠 180 | 0.89 |
| 一様な壁の上の白シールを枠 30 | 0.99 |
| 物体の縁をまたぐ枠 50 | 0.50 |
| テクスチャ背景だけを枠 40 | 1.00 |
| 何もない一様な壁を枠 30 | **0.01** |

合格側はすべて 0.5 以上、滑る側は 0 近傍なので、**0.2** で分かれます。

**1 コマだけでは測れません。** 同じコマで測ると、センサーノイズが「模様」として
効いてしまい、一様な面でも鋭さ 1.0 が出ます（実測）。ノイズは次のコマに同じ形で
現れないので、追跡の役には立ちません。だから測定には必ず別のコマを使います。

滑ると分かったときは、**枠を広げながら測り直して、最初に合格する大きさを探します**。
直径 176px の一様な物体では 50〜120px がすべて 0 近傍で、150px で 0.89 に跳ねました。
輪郭が入ったところで初めて「形の変わらないもの」が枠に入ります。

見つかれば **「枠を ◯px にして置き直す」** が出ます。押すと中心はそのまま、
大きさだけ測った値になった状態で置き直せます。同じコマで置き直すだけなら、
手で指した初速はそのまま生きます。

広げても見つからないときは、**枠の大きさでは解決しません**。その場所に追える
模様が無いということなので、マーカーを貼るか、模様のある部分が入るように
囲み直してください。

既定が「取り直す」なのは、**1 点を直しても足りない**からです。テンプレートが
別のものに乗り移るまでには、たいてい数コマのじわじわしたドリフトが先行します。
移動量が中央値から 3 倍外れた時点でやっと検出できるので、そこまでの数コマは
すでに汚れています。直した 1 点の手前に汚れた点が残り、壊れたテンプレートも
そのままなので、再開すれば同じ場所でまた壊れます。

切り落とすと**トラッカーも全部捨てます**。枠は「残した最後のコマで物体がいた
位置」へ移るので、そのまま置き直して再生を続けられます。

### 1 点だけ消す

グラフを見て後から外れ値に気づくこともあります。修正モード中に **Delete**
で、その時刻のその対象の点を消せます。

対象が別のものに完全に乗り移った点や、物体が隠れて写っていないコマは、
正しい位置が存在しないのでドラッグでは直せません。消すのが唯一正しい処理です。
当てはめも 2 階差分も、1 点の跳ねで台無しになります。

## 探索範囲は「移動量」ではなく「移動量の変化」で決まる

**探索窓は狭いほうが良いです。** 広い窓は、似た模様に乗り移る機会を増やすだけで、
追跡の役には立ちません。

等速度予測が当たっている限り、窓が吸収すべきなのは**移動量ではなく移動量の変化**です。
実測した自由落下では、1 コマ 44px 進む場面でも**予測の外れは 1.1px**でした。40 倍の差です。

それなのに Ver.2.1 までは窓を「枠の大きさ × 探索範囲」で決めていました。枠 40px・
探索範囲 1.2（旧既定）なら半径 48px。必要の 40 倍の範囲を探していたことになります。
**枠を大きくすると窓も比例して大きくなる**ので、「枠を広げる」という対処が
同時に「似た模様に乗り移りやすくする」副作用を持っていました。

合成データでの実測（直径 18px の白シール、経路の外に同じ印が並ぶ）

| 探索半径 | 40 コマ後の最大誤差 |
|---|---|
| 48px（枠 × 1.2・旧既定） | **680px（別の印に乗り移り）** |
| 24px | 0.0px |
| 10px | 0.0px |
| 5px | 0.0px |

一方、速度が急に変わる場面では窓が要ります。衝突で 1 コマの移動が
+18px → −12px に反転する場合、30px の窓が無いと見失います。

そこで現在は

```
普段の半径 ＝ max(4px, 予測の外れ量 × 4 ＋ 3px)   ただし 枠 × 探索範囲 を上限
探索範囲の既定は 1.0（枠の大きさと同じ半径が上限）
縁に当たったら、1 回だけ上限まで広げて引き直す
```

としています。これで両方成立します（上の表の全ケースで 0.0px、衝突でも 0.0px）。
平均の探索半径は 48px → **4〜8px** に下がり、処理も軽くなります。

速度がまだ無い最初の 1 コマだけは、どれだけ動くか分からないので上限で探します。
**2 点目を指しておくとこのコマも狭い窓で済む**ので、速い対象では二重に効きます。

### 飛んだ・見失ったときに出る「次に試すこと」

追跡が飛んで止まったとき、および**解析区間の中で見失ったとき**に、
そのまま押せるボタンが出ます。

- **探索範囲 1.0 → 0.8** — 目印（丸シールなど）を使っているなら、目印そのものは
  見分けがつくので窓は狭いほど有利です
- **再生速度 1/4 → 1/8** — コマを取りこぼすと、記録の上では 1 コマの移動量が
  倍（2 コマ落とせば 3 倍）になり、探索窓を超えます

どちらも下限に達していれば出ません。区間の外で見失った場合も出しません
（もう写っていないだけなので）。

### 画面で確認できます

選択中の対象には、**実際に探している範囲**が薄い点線で出ます。
探索範囲の設定は数字だけでは決められないので、枠と一緒に見て判断してください。
等速で追えている間はごく小さいのが正しい姿です。

### 枠は「大きいほうが良い」わけではありません

枠に求められるのは大きさではなく、**コマが変わっても形の変わらないものが
入っていること**だけです。白い丸シールが背景から分かれて写っているなら、
シールとその周りが入る小さな枠で十分で、広げる意味はありません。

「枠を広げてください」と出るのは、**枠が一様な面の内側に収まっている場合だけ**です
（上のピークの鋭さが 0.2 を下回ったとき）。大きな白い物体の内側だけを囲んだときが
これに当たります。そのときだけ、輪郭が入るまで広げる必要があります。

## 時間軸（スロー動画）

スマホの 240fps スローモーションは **30fps のファイルとして書き出される**ことが多く、
その場合ファイル上の 8 秒が実際には 1 秒です。動画から読める時刻はファイル上の時刻なので、
そのままでは速度が 1/8、加速度が 1/64 になります。

`ControlPanel` の「フレームレートと時間軸」で **撮影 fps**（スマホの撮影設定の数字）を指定してください。

```
実時間 = ファイル上の時刻 × (ファイルの fps ÷ 撮影 fps)
```

ファイルの fps は自動計測されるので、入力するのは撮影 fps だけです。
未指定なら等倍で、通常の動画の挙動は変わりません。
換算が効いているときは、ヘッダー・グラフ全画面・CSV の説明にその旨が出ます。

> **注意**: 以前の版にあった「FPS の手入力」は廃止しました。
> あの値はコマ送りの刻みにしか使われず、自動計測より正確になることがないためです。
> 240 などを手入力すると、コマ送りが 1 回で 1 コマ進まなくなる不具合の原因にもなっていました。

## グラフ概形確認モード

右ペイン `DataPanel` の一番上。**縦軸（x / y / vx / vy / 速さ）** と **横軸（t / x / vx）** を
別々に選ぶ方式で、x-t, y-t, vx-t, vy-t, y-x, vy-vx をすべて含みます。
定番の組み合わせはプリセットのチップから 1 クリック。右上の「拡大」で全画面表示（Esc で閉じる）。

これは飾りではなく **その場で計測が使い物になるか判断するための道具**です。

- **グラフをクリックするとその時刻へ動画がシークします**（再生中なら自動で止まります）。
  vx-t / vy-t に鋭いスパイクが出ていたらそこで追跡が飛んでいるので、クリックして飛び、
  映像の「修正」ツールで直す、という流れになります。
- **カーソルを載せるだけで最寄りの点の t と両軸の値**を読めます。クリックせずスパイクの大きさを確かめられます。
- **y-x と vy-vx は等縮尺**で描きます。縦横の縮尺が違うと放物線が放物線に見えず、形の判断ができません。
  等縮尺のときは右上に「等縮尺」と出ます。
- **見失ったフレームでは線が切れます**。つないで描くと、追跡が飛んだ区間まで滑らかな曲線に見えて
  データが正しいと誤解するためです。
- 物体が複数あるときは色分けして重ね描きし、下の凡例をクリックすると個別に表示を切り替えられます。

描いているのは **平滑化フィルタ適用後の値＝CSV に出るのと同じ数字**なので、
フィルタの効き具合をその場で確認する用途にも使えます。

**表示だけの平滑化トグル**（既定 OFF）を使うと、グラフの見た目からノイズを一段落とせます。
2 次 Savitzky-Golay なので放物線は鈍りません。位置を均し、速度も均した位置から計算し直します。
CSV には影響しません。ただし ON のあいだは追跡の飛びも均されて見えにくくなるので、
**スパイクを探すときは OFF にしてください**（ON のときは画面に注意書きが出ます）。

なお **a-t（加速度）は用意していません**。2 回微分はノイズが支配的になり、かえって誤った印象を与えるためです。

## 平滑化と速度

位置を微分して速度を出すとノイズが Δt で割られて増幅されます。微分の前に平滑化するのが定石です。

- **Butterworth 零位相**（既定・推奨）— 残差の自己相関（Durbin-Watson 統計量）が最小になる
  遮断周波数を 0.5Hz からナイキスト周波数まで走査して自動選択します（Kinovea と同じ方式）。
  X と Y で別々に選びます。
- **Savitzky-Golay** — ウィンドウ幅と多項式次数を指定する方式。

速度は平滑化後の座標の **中心差分**で求めます。前方差分より 1/2 フレーム分の位相ずれがなく、ノイズにも強い方式です。

### どちらを選ぶか

合成データ（自由落下）で速度カーブの点ごとの誤差を比べた結果です。

| 条件 | Butterworth 自動 | Savitzky-Golay 7点 |
|---|---|---|
| 手動記録 40 点（40ms 間隔） | **−57 %** | +131 % |
| 手動記録 20 点 | **−45 %** | +76 % |
| 自動追跡 30fps・200 点 | **−33 %** | +1335 % |
| 自動追跡 240fps・300 点 | **−77 %** | −47 % |

（フィルタ OFF を基準にした増減。マイナスが改善）

**Butterworth はどの条件でも改善します。** 遮断周波数をデータから決めるので、
サンプリング間隔に自動で追随するためです。手動記録のように点数が少ない場合も有効です。

**Savitzky-Golay は窓を「時間」で考える必要があります。** 同じ 7 点でも 240fps なら 29ms、
30fps なら 233ms を均すことになり、後者では運動そのものが削られます。
有効なのは窓が 20〜40ms 程度のときだけです。
UI には「この設定で均す時間」を ms で表示し、長すぎる場合は警告を出します。
迷うなら Butterworth を使ってください。

## 解析（当てはめ）

右ペインの「解析（当てはめ）」 で、記録したデータに直線か放物線を当てはめて数値を出します。

グラフ概形の確認とは**別の作業**として分けてあります。あちらは「計測が
使い物になるか」を見る場所で、平滑化も効きます。こちらは「数値をいくつとして
報告するか」を決める場所なので、次の 3 つを外しません。

### 1. 当てはめるのは生データ

平滑化したデータに直線を当てはめると、**傾きはほとんど変わらないのに
R² と標準誤差だけが良くなります**。平滑化は隣の点と相関を作る操作なので、
最小二乗の前提である「独立な n 点」が崩れ、不確かさが実際より小さく出ます。
生徒に「誤差 0.3%」と読ませてしまうのがいちばん良くないので、
当てはめは記録された座標そのままに対して行います。

速度は生の座標から中心差分で出し直します。見失った点と、追跡が飛んだと
判定された点（✕ の付いた点）は当てはめから除きます。

### 2. 傾きには標準誤差を添える

```
se(傾き) = s / √Sxx       s は残差の標準偏差、Sxx = Σ(t − t̄)²
```

傾きだけ見せると、8 点でも 200 点でも同じ重みで読まれてしまいます。
この式には点数と**区間の広さ**の両方が入っているので、「区間を広く取るほど
誤差が下がる」という当たり前のことが数字で見えます。

加速度として読める組み合わせのときは、そのまま加速度を出します。

| 当てはめ | 読み方 |
|---|---|
| vy-t に直線 | 傾き = 加速度 |
| y-t に放物線 | t² の係数 × 2 = 加速度 |
| x-t に直線 | 傾き = 速度（等速のとき） |

単位が m のときは **g の何倍か**も出します。

数値計算の注意点として、時刻は平均を引いてから当てはめています。
t が 2.4 s 付近で幅 0.3 s しかない区間を素のまま 2 次で解くと、正規方程式の
条件数が 10⁷ 台まで悪化して係数が桁で狂います（実測）。平均を引くと 10⁴ 台に
収まり、最高次の係数は平行移動で変わらないので読みは同じです。

### まず絵で見せる

**データの点と、当てはめた線**を重ねて描きます。青い点が実測、白い線が当てはめた
直線（または放物線）です。軸には量と単位が入ります。

数値だけ、あるいは残差だけを出しても「何に何を当てはめたのか」は伝わりません。
線がデータに乗っているかどうかは、絵を見れば一目で分かります。

そのうえで、読み取れる値を 1 つ大きく出します。

```
加速度 = -9.75 ± 0.04 m/s²      g の 0.994 倍
```

**± は傾きの標準誤差**です。点が多いほど、区間が広いほど小さくなります。

### 矩形で範囲を選べます

グラフの上をドラッグすると、**その矩形の中の点だけで当てはめ直します**。
横は時間、縦は値の範囲なので、「この時間帯の、この帯に乗っている点」という
選び方ができます。

直線になっている区間だけを取りたいとき（投げ上げの、手を離れてから着地までの間
だけ、など）に効きます。選ばなかった点は灰色で残るので、**何を外したかが
見えたまま**になります。小さくなぞる、またはクリックすると解除です。

当てはめた線も、選んだ範囲の中だけに引きます。外まで伸ばすと、選んでいない
区間まで当てはめたように見えてしまうので。

### a-t 図

加速度の時間変化を、位置の 2 階差分で出せます。**Δt を選ぶ**のが前提です。

```
a = (y[i+k] − 2 y[i] + y[i−k]) / (k dt)²
```

Δt のボタンには**実時間**が出ます（コマ数ではなく）。判断の基準が実時間だから
です。合成データで確かめた目安は **30ms 前後**で、240fps なら 8 コマ、30fps なら
1〜2 コマがそこに当たります。既定はこの条件を満たす最小の Δt が自動で選ばれます。

| 条件 | Δt | 平均 a | ばらつき |
|---|---|---|---|
| 240fps・位置ノイズ 0.5mm | 4.2ms (1 コマ) | −9.26 | **80.9** |
| 〃 | 16.7ms (4 コマ) | −9.75 | 4.5 |
| 〃 | 33.3ms (8 コマ) | −9.86 | **1.1** |
| 30fps・位置ノイズ 2mm | 33.3ms (1 コマ) | −9.79 | 3.7 |
| 〃 | 66.7ms (2 コマ) | −9.83 | **1.1** |

白い線が平均、帯が ±標準偏差です。当てはめから出した加速度も並べて出すので、
**別々の出し方で同じ答えになるか**を確かめられます。

矩形で範囲を選んでいるときは、a-t もその時間帯だけで出します。

### 飛んだコマは外して当てはめます

コマの点検（位置の 2 階差分）で「飛んでいる」と判定されたコマは、**既定で
当てはめから外します**。残差が RMSE の 3 倍まで伸びる原因はたいていこれで、
入れたままだと傾きも標準誤差も壊れます。

ただし**黙っては外しません**。外した数を出して、ワンタップで戻せるようにして
あります。都合の悪い点を黙って消すのは、数値を出す道具としていちばん
やってはいけないことなので。

見失った点と、追跡が飛んだと判定された点（✕ の付いた点）も同じく外します。

### 3. 残差を見せる

残差（実測 − 当てはめ）を並べて描きます。**ばらついているだけなら、その
モデルで足りています。弓なりに曲がっていたらモデルが違います**（直線を
当てはめた速度が曲がる＝加速度が一定でない）。RMSE の 2.5 倍を超えた点は
橙で大きく出て、押すとその時刻へ飛びます。

残差は診断の道具なので、既定では畳んであります。帯は ±RMSE で、点の 2/3 ほどが
この中に入るのが素直な姿です。

### Δt の選び方（2 階差分で加速度を出す場合）

```
a = (y[i+k] − 2 y[i] + y[i−k]) / (k dt)²
```

分母が (Δt)² なので、**Δt を 2 倍にするとばらつきは 1/4** になります。
一方で Δt を広げると「その区間で加速度が一定」という前提が効いてくるので、
等加速度でない運動では平均が偏ります。

k ごとの平均とばらつきを並べて出すので、**平均が動かなくなって、ばらつきが
十分小さい最小の Δt** を選んでください。合成データ（240fps・位置ノイズ
0.5mm の自由落下）での実測が目安になります。

| Δt | 平均 a | ばらつき (SD) |
|---|---|---|
| 4.2 ms (1 コマ) | −9.47 | **64.0** |
| 8.3 ms (2 コマ) | −9.78 | 18.3 |
| 16.7 ms (4 コマ) | −9.74 | 4.1 |
| 33.3 ms (8 コマ) | −9.80 | **0.88** |

1 コマ差では使い物になりません。これが「スロー撮影したのに加速度が暴れる」
のいちばん多い原因です。

### 単位は m にそろえます

基準の長さは **cm や mm で入力して構いません**（A4 なら 29.7cm のほうが自然です）。
ただし**記録と出力は常に m・m/s・m/s²** です。教科書の式にそのまま入りますし、
CSV・グラフ・解析で桁が食い違うこともありません。

校正していないあいだは **px・px/s・px/s²** のまま出ます。その状態では g との
比較も出しません（比べても意味がないので）。

### 誤差の効き方

**スケールの誤差は加速度に比例、時間軸の誤差は 2 乗で効きます。**
撮影 fps を 2 倍間違えると加速度は 4 倍ずれます。校正の基準が 33px しか
ないときは 1px が 3% に相当するので、そこも加速度にそのまま乗ります。

## データの取り出し

`DataPanel` から 2 種類の CSV を出せます（どちらも BOM 付き UTF-8 / Excel 対応）。

### CSV ダウンロード（すべて）

出力列: `Timestamp` / 各物体の `X(px), Y(px), X, Y, Vx, Vy, Speed, Score, Lost, Manual` / 物体間距離

`Score` はマッチングスコアです。追跡の信頼度を後から検証できます。
`Manual` は手動で位置を直したフレームの印です。

### 位置だけの CSV

出力列: `Timestamp` / 各物体の `X, Y` だけ。速度も加速度も入っていません。

**平滑化をかけていない生の位置**を出します。位置から速度を求める過程そのものが
学習の中身なので、こちらのフィルタを通した値を渡してしまうと、差分を取ると
なぜノイズが荒れるのか、なぜ平滑化が要るのかを手を動かして確かめられなくなるためです。
そのぶん、この値は画面のグラフや上の CSV とは一致しません。

見失ったコマは空欄にしてあります（0 を入れると原点に居たように読めてしまうため）。

### 単位

**出力はすべて m です。** 速度は m/s、加速度は m/s² になるので、教科書の式にそのまま入ります。
基準の長さを入力する欄だけは cm / mm を選べます（A4 を 29.7cm と入れられるように）。
未校正のときは px のままです。画面のグラフ・計測値・CSV はすべて同じ単位なので、
桁が食い違って見えることはありません。

## 精度を出すコツ

- 枠は 20px 以上、できれば 30px 前後。**必要以上に大きくしない**
- **枠の中を物体の面で埋める**（動かない背景が入るほど精度が落ちます。形状の差より一桁効きます）
- **探索範囲は小さめで良い**（広い窓は似た模様に乗り移る機会を増やすだけ。
  等速度予測が効いている間、窓が吸収するのは移動量ではなく移動量の変化）
- マーカーは**白い丸シールではなく、印刷したもの**を使う（回転しない対象は太い十字、回る対象は同心円）
- 斜めから撮った映像は必ず平面（四隅）校正
- 取りこぼすときは再生速度を落とす。確実にしたいなら **「全コマ処理」**（実測で 100%）
- 追跡が飛んでいないかは、必ず **vx-t / vy-t のグラフで確認**する
- スロー動画では **撮影 fps を必ず設定**する（忘れると加速度が 1/64 になります）
- 頭と尻の使えない時間は **解析区間**で外す（フィルタの自動遮断周波数が運動区間だけを見るようになります）
- 手動記録では **細かく打ちすぎない**（実時間で 30〜50ms の間隔を空ける）

## 技術

React 18 + TypeScript + Vite / OpenCV.js（`@techstark/opencv-js`）によるテンプレートマッチング。
サブピクセル補間は相関マップのピーク近傍 3×3 に 2 次曲面を最小二乗フィットして求めます
（実測でガタつきの 2 階差分 RMS が 1.06px → 0.35px）。

フレーム処理は `requestVideoFrameCallback` を使い、提示された実フレームごとに 1 回だけ行います。
時刻は動画本来の `mediaTime` を使うので、画面の描画周期に引きずられません。

コマ送りも同じ考え方です。`currentTime += 1/fps` で進めた「要求時刻」ではなく、
シーク後に **実際に表示されたフレームの `mediaTime` を読み直して**記録します。
これで fps の推定は「どのコマに着地するか」だけを決め、記録される時刻には影響しません。
fps を 20% 誤って推定していても、時刻の誤差は毎コマ自己修正されます（`src/utils/videoFrame.ts`）。

### スマホ版との共通コード

`src/utils/` と `src/types/` は [tracker_mobile](https://github.com/Shin-phys/tracker_mobile) と
1 行も違わないので、**この PC 版を正として同期**しています。

```bash
npm run sync:core        # スマホ版へコピー
npm run sync:core:check  # 差分があれば異常終了（コミット前の確認用）
```

共通コードを直すときは必ずこちら（PC 版）を編集してください。
同期先は隣のフォルダを中身で自動判別します（`TRACKER_MOBILE_DIR` で明示指定も可）。
UI（`src/components/`）は両者で別物なので共有していません。
